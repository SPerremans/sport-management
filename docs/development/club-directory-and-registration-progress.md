# Club directory and member registration progress

Updated 17 October 2026.

## Find a club

Both `Club_Directory` and the dashboard's Find a club tab show one comparison table: Club, City, Sport, Players and View club. Fees and registration actions remain on `Club_Detail`; nested fee tables have been removed from search results.

The filters are club-name text, searchable City/Sport/Age groups/Playing level multiselects, and an optional Age in years. Multiple choices within a filter are alternatives; separate filters combine. All membership-related conditions must match the same eligible membership: youth badminton plus adult tennis does not advertise youth tennis. Selected values remain removable chips above the search input while another value is searched. Selected options appear first in each dropdown, followed by the remaining choices in stable order; displayed and keyboard order agree. Clicking anywhere on a row toggles it, including its decorative checkbox/label area. Empty selection means all. Choices come from published clubs and their current eligible offers, rather than fixed enum options. Filters apply on change/Enter. A Reset filters button above the controls clears name, age and every multiselect without form validation, including malformed age input. An empty result shows a clear message.

The [17 October federation update](federation-affiliation-and-accounts.md) replaces manual club Sports with sports derived from approved federations and eligible membership offers. The old stored Club.Sports/AgeGroups/PlayingLevel values are retained for compatibility but are no longer read or edited by these views.

`ClubDiscoveryProfile` is a read-only, non-persistent projection shared by the directory and club detail. It uses only available fees in the current published season and membership types whose availability dates include today, matching `DS_Club_Offers`. `IsCompetitionPlayer` identifies Competition memberships; other offered memberships contribute Recreational. Categories and identical age ranges appear once even if multiple types/fees share them. Clubs with no current offers say No memberships currently available. No summary is persisted or refreshed in the client by a data-source microflow, so fee/type/date changes are reflected when the view reloads. The directory bulk-loads fees and membership types before looping; it does not run a database retrieve per club or fee.

Membership types define inclusive `MinimumAge` and `MaximumAge` in whole years. Zero means no lower/upper restriction; both zero display All ages. Negative bounds and a nonzero maximum below the minimum are rejected through the existing save validator. The editor, membership-type table, and available-offers table expose these ages. Summaries retain separate intervals, for example 6–17, 18–35, 40–65, rather than inventing coverage across gaps. A currently offered unrestricted membership makes the overall summary All ages. The exact-age filter accepts whole years (0–999), checks these bounds and safely returns no results for malformed input.

Membership editors explicitly select one or more of Youth, Adults and Seniors using `AudienceYouth`, `AudienceAdults` and `AudienceSeniors`. These categories are independent of numeric limits; there is no universal inferred senior threshold. Directory and detail summaries deduplicate the categories across eligible offers. Age choices appear in Youth/Adults/Seniors order, only when offered. Playing-level choices are Competition and Recreational when available. There is no combined Both or Not specified filter option: select multiple atomic choices instead. Existing memberships retain false flags until configured; their numeric age ranges remain searchable. These are discovery descriptions, not automatic registration rejection rules.

Directory rows reference their club and city; View club rechecks publication on the server. Existing scoped membership-type update permissions govern age and audience edits, including authorized staff and platform administrators. `ClubDiscoverySearch` exposes only transient name, age and selection references for editing; profile, offer and choice objects remain read-only. No new persistent entity or cleanup type is introduced.

`ClubDirectoryCity` is a read-only reference catalogue. `Club.City` remains authoritative. `BCO_ClubDirectory_SyncCity` updates its derived association when a club is saved. Startup calls `ASU_ClubDirectory_BackfillCities` after the existing startup actions. The helper preloads cities, compares trimmed case-insensitive names in memory, batches new-city commits outside its loop, and returns only changed clubs. It does not send client refreshes or seed sample data. Empty city text clears the association; unused catalogue rows are not displayed by the directory.

Both views now use a search DataView and the installed Combobox widget with context association selections and server-generated choice lists. They share `DS_ClubDiscovery_Search`, `DS_ClubDiscovery_Choices`, `DS_ClubDiscovery_Results` and clear/refresh actions under Discovery/Filters. The directory is loaded once into a non-persistent graph; subsequent filters traverse that graph in memory. Choice ordering partitions the sorted list using the search's four selection reference sets; it neither changes the choice objects nor the selection. Data sources neither commit records nor refresh objects in the client. Compact checkbox, chip and control styling is shared in `_nexio-tables.scss`; decorative checkbox/label hit areas defer pointer events to the listbox row, retaining its native keyboard behavior. The former grid Drop-down filter metadata is no longer used in these views.

The on-change microflow explicitly reads and retains all four current selection associations before refreshing the non-persistent search. An empty Change Object action exported `a:[]` in `deployment/model/microflows.json`, omitting these associations from that action's incoming request graph. This could refresh older server selections while visible chips reflected newer client state. The corrected export must include Cities, Sports, Ages and Levels on `ClubDiscoverySearch`. Do not reduce this handler to an empty refresh again. This addresses a concrete request-graph omission; browser confirmation of the reported Mechelen/Gent mismatch remains pending.

## Member dashboard

Tabs: Important news, Upcoming events, My registrations, Invoices, Find a club. The former My clubs table is now under My registrations as Other memberships, limited to memberships that have no corresponding registration request. This retains imported/direct membership records without repeating a membership already represented by a request.

Registration columns are Club, Membership, Season, Status, Payment, Next action and Actions. `DS_Member_Registrations` retrieves only the current user's requests and orders them as drafts, awaiting approval, waiting list, awaiting payment, active, and closed history; newest submitted requests come first within each group. The data source performs no writes or client refreshes.

Club staff with Registrations Read and Update can put a pending application on hold. It remains Pending with Approval = OnHold and can subsequently be approved through the existing approval form. The former routine Reject button in the club workspace is replaced with Put on hold. Historical rejection records and their logic remain intact.

Members can withdraw their own draft, awaiting-approval or waiting-list application. The action reloads persisted ownership and eligibility, so another person's request or an approved request cannot be withdrawn by submitting an ID or using an old page. Withdrawal retains the request and its answers with Status = Withdrawn, cancels an unpaid registration invoice if present, synchronizes federation registration state, and treats a linked renewal offer as declined. A paid invoice requires club resolution. Existing active membership is not cancelled by withdrawing a renewal application.

`SUB_Registration_UpdateState` returns immediately for Withdrawn and Cancelled requests, preventing later state recalculation from reactivating them. Existing payment application already requires a Pending request with approved/not-required approval and Payment = Required. Holding an application does not create an invoice or activate membership.
